# NordPSA fixtures

Reservoir operating limits, taken from [NordPSA](https://github.com/beow/NordPSA) —
a Nordic power system model on PyPSA — to validate `HydroOps` in `network-lopf`.

## Why this directory is separate from `goldens`

`reference/goldens` is generated by `reference/generate_goldens.py` from networks
that PyPSA itself ships or that the generator builds. These come from another
repository, and one property of them is the whole reason they exist.

NordPSA imposes its operating limits through PyPSA's `extra_functionality`
callback. A callback adds rows to the linopy model at solve time and stores
**nothing** on the network, so an export carries the buses, the inflow and the
`spill_cost` but not one of the limits. Read the exported network back, solve it,
and you get a different and strictly easier problem — with a cheaper objective,
which looks exactly like a port under-counting something.

So the network and the answer have to travel separately: `networks/` holds what the
export can carry, and `hydro.json` holds what the callback did on top of it.

## Layout

- `networks/inflow<N>-cheap<M>/` — PyPSA CSV exports, one per distinct network.
  Five variants because NordPSA varies inflow and cheap-generator capacity per
  scenario to put each limit on the binding side; with cyclic state-of-charge the
  horizon's production equals its inflow, so a floor under that mean or a ceiling
  over it changes nothing and would prove nothing.
- `hydro.json` — per case: the operational config, the objective PyPSA reached
  under it, and the normalised daily/weekly ratios and spill. The config is read
  from here by `HydroOpsSuite` rather than restated in Scala, so the two sides
  cannot drift.
- `generate.py` — regenerates both.

## Regenerating

Needs PyPSA 1.3.0 — the version `goldens/manifest.json` is pinned to, and the one
NordPSA states it is verified against. No data tokens are needed: the network is
NordPSA's own synthetic test fixture, not a fetched Nordic dataset.

```bash
git clone https://github.com/beow/NordPSA.git
uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python "pypsa==1.3.0" "highspy>=1.15" pandas numpy scipy pyarrow pyyaml
uv pip install --python .venv/bin/python -e ./NordPSA
.venv/bin/python generate.py <output-dir>
```

`generate.py` expects `NordPSA/` beside it, and imports
`nordpsa.constraints.hydro_operation_constraints` — the production callback, not a
copy of it. That import is the point: a reimplementation here could agree with
itself while disagreeing with NordPSA.
